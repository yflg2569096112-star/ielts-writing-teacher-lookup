# Workflow Insights · 工作流复盘与可迁移洞察

> 这份文档是项目作者（写作辅导老师 + LLM 协作者）从一次"LLM 辅助备课工具链"实战里提炼的可迁移内容。
> 主要给将来的自己看；同时给参观作品集的同行、PM、开发者看。

## 0 · TL;DR

| 类别 | 1 句话 |
|---|---|
| 项目本身 | 把散在 Word/HTML/PPT 多个文件的备课讲解，做成一页可搜索 HTML，老师讲台 3 秒内能定位到任意一题 |
| 最值的设计判断 | "够用就好"的模糊搜索，反对加同义词/拼音/AI 排序 |
| 最值的工作流学习 | 文件命名规范是 LLM 协作的前置条件，不是事后整理 |
| 最容易迁移的模式 | 静态 HTML + Python builder + 数据驱动配置，适合任何"单人/小团队 + 离线优先 + 数据频率低"的工具场景 |

## 2 · 核心设计决策与权衡

### 决策 1 · 纯静态 HTML，不做 SaaS

**为什么：**
- 老师讲台的 3 秒决策窗口里没时间等 API 响应
- 单老师场景 + 学校网络封锁 + USB 拷给同事——纯静态是最低阻力
- 不用维护后端 = 不用在睡前担心服务挂了第二天讲台用不了

**Trade-off：**
- 题目数据 baked-in，更新需要重跑 builder（接受）
- 没有用户系统，无法多人协作（接受，单老师场景）

**可迁移：** 凡是"单人 / 小团队 + 离线优先 + 数据更新频率低"的场景，先考虑纯静态。SaaS 不是默认选项。

### 决策 2 · 写 Python builder，不手写 HTML

**为什么：**
- 53 道题 × 5 个字段 × 多种讲解 anchor，手写 HTML 一定会出错
- 数据来源是 Word 备课稿（结构化数据），需要程序化提取
- 一旦定位逻辑变更（增加题号、调整分类），重新生成成本极低

**Trade-off：**
- 初学者读不懂 builder（接受，加注释能缓解）
- HTML/CSS/JS 全部 inline 在 Python f-string 里——模板抽离是技术债（< 800 行时不抽，> 1500 行再抽）

**可迁移：** 教学材料的"内容生产"和"展示形态"必须分离。内容用结构化数据存（YAML/JSON/CSV），展示用模板生成。

### 决策 3 · `normalizeText` 的"够用就好"原则

只做三件事：

```javascript
.replace(/第\s*0+(\d+)\s*题/g, '第$1题')  // 第 01 题 / 第 1 题 都归一化
.replace(/[\s,，.。:：;；/\\|\-—_>]+/g, '') // 删空白和标点
.replace(/第0+(\d+)/g, '第$1');           // 删数字前导零
```

**没加什么 + 为什么不加：**
- 没加拼音搜索：教师场景里 "Gap year" 比 "jianxinian" 快
- 没加同义词扩展：教学语境里"双饼图"和"两个饼图"是设计者的选择，不该被搜索引擎抹平
- 没加 fuzzy edit distance：误命中比漏命中代价高得多

**关键 insight：模糊搜索的目标不是召回率，是让老师在讲台 3 秒内确认结果。** 太"聪明"的搜索会让老师怀疑结果对不对，浪费的反而是 3 秒里的 1-2 秒。

**可迁移：** 内部工具的搜索体验 ≠ 搜索引擎的搜索体验。简单可预测 > 智能不可控。

### 决策 4 · 数字搜索范围限定 1-30

**为什么：**
- 题库实际范围 ≤ 30，超出这个范围的数字（年份、百分比）应当走标准模糊搜索
- 否则裸输入 "1" 会误命中 "1970"、"1995"、"10%" 等所有含数字的行

**Trade-off：**
- Hardcode 数字 30，未来题库扩展需要改一行代码（接受，加注释 + TODO）

**可迁移：** 当一个判断逻辑依赖"业务上下文的真实分布"时，把这个分布约束写进代码，而不是写在注释里。

## 3 · LLM 协作的 3 个真实阻碍

### 阻碍 1 · 文件命名 > 模型能力

最早卡住的不是 LLM 答得对不对——是我把 5 个版本的 `第1次课_Unit1-2_xxxx.md` 一股脑塞给它。它不知道哪个是最新，我也忘了哪个是最新。

仓库里现在保留的 `PPT_第X次课UnitY-Z_v[N]修改对比.md` 这种命名规则，就是被这个阻碍逼出来的。

**修正：** 强制文件名 = 用途 + 版本号 + 状态（draft / confirmed / archived）。命名规范是 LLM 协作的前置条件，不是事后整理。

### 阻碍 2 · 教学颗粒度 > 模型上下文长度

让 LLM "帮我写 Gap year 雅思大作文讲解" → 它给 5000 字全面讲解。
但实际课堂上我用的颗粒度是"60 秒讲一个知识点"。

LLM 没有"课堂时间槽"的概念，需要我把颗粒度作为 prompt 约束传进去。

**修正：** 教学 prompt 必须包含三个约束：
1. **时间槽**：多少秒讲完
2. **目标人群**：高分还是底分学生
3. **上下文模式**：讲台讲 / 课后回看 / 学生自学

### 阻碍 3 · 评估 > 实现

"这个讲解版本对学生有用吗？"——LLM 无法回答。只能我带到课堂里试，下课问 3 个学生，第二周再迭代。

仓库里"v1 确认版"、"v2 修改对比"、"v3 美化版"这种迭代脉络，就是这个反馈循环的副产物。

**修正：** 教学工具的 v1 不要追求闭环，要追求"可被讲台快速试错"。

## 4 · 可迁移的 5 个模式

### 模式 1 · 教师工具的 UI 阈值比 ToC 产品低 70%

老师不要花哨。第一版能跑、能搜、能跳就够。**美化是 v2，不是 v1 的 gate。**

这个检索页用了一套朴素的 CSS 变量 + 表格布局，没有 Tailwind、没有 React、没有动画库。讲台上用起来一点不卡。

### 模式 2 · 讲台 3 秒决策窗口

学生问"老师第 X 题怎么讲" → 老师讲台上有约 3 秒决策窗口。超过这个窗口学生注意力转移，回不来。

工具设计必须假定"3 秒内结果不出 = 失败"。所以：
- 即时搜索（每次按键 < 100ms 渲染）
- 模糊匹配 5 种常见输入
- 一键跳转，不需要二次确认

**可迁移：** 内部工具如果有"决策时间窗口"，把这个窗口数值化、写进设计约束。

### 模式 3 · 静态 HTML + 数据驱动生成器

对小团队 / 单人 / 离线场景，这个模式比 SaaS 实用 10 倍：

| 维度 | 静态 HTML | SaaS |
|---|---|---|
| 部署成本 | 0 | 有 |
| 维护成本 | rebuild 即可 | 持续运维 |
| 失败模式 | HTML 渲染失败（基本不会） | 服务挂、Cookie 过期、限流 |
| 离线可用 | ✓ | ✗ |
| USB 拷给同事 | ✓ | ✗ |

**可迁移范围远超教学工具：** 任何"一个人或小团队的内部参考工具"都可以考虑。

### 模式 4 · 模糊搜索的"够用就好"原则

教师工具的搜索目标是：
1. 减少老师输入字符数（输 "第 1" 而不是 "图表作文练习 静态图 第 01 题"）
2. 在 3 秒内给出可信结果（智能 = 不可信）
3. **不出现意外结果**（关键！）

第 3 条最容易被忽视。智能搜索的代价是结果不可预测，老师不敢用。

**可迁移：** 内部工具的搜索设计应该向"快捷键 + 索引"靠拢，向"自然语言搜索"远离。

### 模式 5 · 教学颗粒度作为 prompt 的第一约束

任何让 LLM 帮做教学内容的场景，第一句 prompt 应该是颗粒度约束，不是任务描述。

| | Prompt | LLM 给的东西 |
|---|---|---|
| ❌ 反例 | "帮我写一个 Gap year 雅思大作文讲解" | 5000 字全面讲解 |
| ✅ 正例 | "帮我写 90 秒讲台讲解，针对 5.5 目标学生，讲清楚 Gap year 题型的 outweigh 结构" | 约 300 字 + 板书结构 |

## 5 · Anti-patterns（曾经想做但发现不该做）

### Anti 1 · 加同义词 / 拼音 / 双语映射搜索
Codex code review 时建议加。但教师场景里同义词扩展会引入不确定性，老师不敢相信搜索结果。**砍掉。**

### Anti 2 · 把工具做成"通用搜索引擎"
一度想扩展成支持模糊语义搜索（向量化 + 排序）。但教师讲台不需要、也没时间相信"为什么这条排第一"。**砍掉。**

### Anti 3 · 把 HTML/CSS/JS 都抽到独立文件
听起来"工程化"，但 builder 还很小（< 800 行）时，inline 在 f-string 里反而方便维护和阅读。**延后到 > 1500 行再考虑。**

### Anti 4 · 一开始就追求"通用框架"
最早想做"通用教学材料管理框架"，但具体到一个备课流程才发现：通用化的代价是任何一种考试都装不下。**先把一个考试做对，再抽象。**

## 6 · 跨场景迁移示例

底层抽象：**"题目集 + 多版本讲解 + 可定位 anchor"在任何题库辅导场景都成立。**

| 场景 | 怎么迁 |
|---|---|
| IELTS 写作 → TOEFL 独立写作 | 替换题目数据 YAML，分类换成 Education / Society / Technology 等 |
| IELTS 写作 → GRE Issue/Argument | 数据换 GRE 官方题库，anchor 跳转换成对应讲解 |
| IELTS 写作 → 四六级写作 | 数据换四六级真题，分类换成命题作文 / 应用文 |
| 写作 → 听力错题讲解 | 数据从"题号 + 题干"换成"题号 + 错题点 + 讲解 anchor" |
| 写作 → 阅读题型库 | 同上，加题型筛选（细节题 / 推理题 / 主旨题） |
| 语言培训 → 编程题库 | 数据换成 LeetCode 题号 + 自己的题解 anchor |
| 教学 → 法律 / 医学辅导 | 数据换成案例编号 + 教学讲解 anchor |

## 7 · 给三类人的建议

### 给老师：如果你想做类似工具
1. 先把备课材料结构化（YAML / Markdown 表）。**这是 1 周的事，不是 1 天**
2. 然后写一个最简单的 Python builder（50 行），别用 React、别用框架
3. 第一版在自己讲台上用 1-2 周，再决定要不要加功能

### 给 PM：如果你想做教学工具
1. **先去讲台旁边蹲 3 天**，记录老师讲台 3 秒决策窗口里发生的事
2. 不要默认 ToC 产品的 UI 经验，教师场景比 ToC 简单得多
3. 评估指标不是 DAU，是"讲台真实使用次数"

### 给开发者：如果你想接 LLM 教学场景
1. 第一卡点是数据结构化，不是模型能力
2. 第二卡点是教学颗粒度的 prompt 设计
3. 第三卡点是评估难做——准备好"用户带回讲台试用"的反馈循环
